Making complex APIs easier to understand

For Global Payments’ API Explorer, I designed a reusable parameter structure and connected code examples to the properties they use. The redesign gave developers a way to identify relevant fields while keeping the full API reference available. An internal team later described the example-highlighting feature as “game changing.”

My role
Product designer
Team
I partnered with a fellow designer, a product manager, a researcher, and a developer
Focus
API documentation + developer experience

The problem: complete information, unclear relevance

Complete documentation was difficult to apply to a specific use case. API Explorer presented a large volume of properties and configurations. Developers needed to work out which fields applied to their task, how nested properties related, and how definitions translated into a request. That interpretation work stood between reading the documentation and using the API.

The approach: connect definitions to examples

Connect the reference to the task at hand. I focused on three decisions: create a consistent parameter template, progressively reveal nested detail, and connect selected examples to relevant properties. I developed the structure and interaction designs in collaboration with the project team.

Understanding how developers use the reference

The project included user testing to understand how developers approached the documentation and testing tools.

Research explored how they found relevant information, interpreted properties, and moved between documentation and examples. These observations helped frame where clearer guidance was needed.

The insight: documentation needs context

Complete documentation still needs context.

Showing every available property gave developers a complete reference, but left them to determine relevance. The design direction was to keep the full documentation accessible while using examples and a clearer hierarchy to guide exploration.

Competitive analysis

I reviewed how Square, Stripe, and Adyen approached API documentation. I captured screenshots and analyzed each experience’s structure, including how navigation, parameter information, and examples were organized.

I applied the same analysis to our existing design. Documenting our structure alongside the competitors gave me a consistent basis for comparison and helped identify where our information hierarchy could be clearer.

One reusable structure for five parameter groups

I began by breaking the existing experience into its core parts: navigation, endpoint descriptions, parameters, request examples, and response information. This helped me understand what belonged together and what needed a clearer separation.

From recurring parameters to one reusable component

I made the technical content manageable by looking for recurring structures across endpoints. I identified five recurring parameter groups and broke down the structure of each to understand what they shared and where they differed.

That analysis led to one reusable parameter component. It accounted for nested components, properties, example values, and required or optional status. Individual pieces could be shown or hidden depending on which parameter group used the template.

Reveal nested details when developers need them

Show an overview, then reveal the detail.

Nested API properties can turn a reference page into a long document that is difficult to scan. I explored collapsed and expanded states to establish how much information should appear at each level.

The initial view stays scannable; technical detail remains available. Developers can expand the properties they need to investigate, with definitions and examples alongside one another to connect a field’s meaning with its use.

Make the connection between examples and properties visible

During a feedback session, a fellow designer suggested a way to make examples more useful: after selecting an example, a developer could turn on a toggle to highlight the properties used in that specific example.

Select an example. Highlight the properties it uses.

The feature connects a practical example to the full reference. Developers can see which fields are relevant to the selected example while keeping the rest of the documentation available.

Tradeoffs: validate understanding first, measure efficiency next

Within the project timeline, research prioritized qualitative evidence for the proof of concept. Following the research team’s recommendation, we focused on understanding how developers interpreted the experience. This helped inform the design direction, but left a gap in measuring the size of the improvement.

I can explain the design rationale and share qualitative feedback. I cannot claim a measured reduction in task time, errors, or support requests. A follow-up evaluation would need a baseline and comparable tasks to assess those outcomes.

Simplifying the reference also meant balancing scanability with completeness. Progressive disclosure kept nested detail available, but required developers to expand it. Example-specific highlighting added context while preserving access to properties outside the selected example.

Next steps: test the path from documentation to a request

I would ask developers to identify the required fields for a scenario and build a request, comparing the previous experience with the redesign. Task completion, time on task, incorrect field selections, and backtracking would help assess whether the new structure improves practical use.

I would also observe whether developers discover the highlighting toggle and understand that it relates to the selected example. That would help determine whether the feature needs clearer labeling or guidance.

Reflection: use patterns to navigate complexity

Breaking unfamiliar content into recurring parts gave me a way forward. Comparing five parameter groups led to an adaptable component that could accommodate shared elements and differences.

The strongest interaction came through collaboration. A fellow designer’s suggestion for example-specific highlighting strengthened the connection between reference content and practical use. My contribution was part of that shared design effort.

This project reinforced the value of pairing a clear information structure with contextual guidance and of planning measurement alongside qualitative validation.
