Helping developers find the meaning in complex APIs

API Explorer gave developers a detailed reference for building payment integrations. My challenge was to help them connect that information to what they were trying to do.

My role
Product designer
Team
I partnered with a fellow designer, a product manager, a researcher, and a developer
Focus
API documentation + developer experience
View live website

The information was there. The context took work.

Before a developer could build a request, they had to understand which properties applied to their use case and how those properties fit together. API Explorer presented a large volume of technical detail, leaving developers to make those connections themselves.

I wanted to make that interpretation easier. The full reference still needed to be available, but the interface could do more to help developers find their starting point.

I started by taking the experience apart.

The project included user testing to understand how developers found information, interpreted properties, and moved between documentation and examples. Alongside that research, I reviewed Square, Stripe, and Adyen, comparing how they organized navigation, definitions, and code examples.

I mapped our existing experience in the same way. Breaking it into smaller parts helped me see where the relationships between information could be clearer.

The direction became clear: keep the reference complete and give developers more context as they explore it.

Five parameter groups. One adaptable structure.

I found five recurring parameter groups and translated their shared elements into one reusable component. The template accommodated nested properties, example values, and required or optional status, with elements shown or hidden to fit each group. Finding that pattern gave me a way to organize unfamiliar technical content into a consistent experience.

A useful idea emerged through feedback.

During a feedback session, a fellow designer suggested connecting the selected example to the properties it used. A developer could choose an example and turn on a toggle to highlight those properties in the reference.

This gave the example a role beyond showing code. It became a guide to understanding which fields mattered, while the rest of the documentation stayed available.

The next challenge was how much detail to show.

Nested properties could turn a reference page into a long document. I explored collapsed and expanded states so developers could begin with an overview and open the details they needed.

That choice came with a tradeoff. Collapsing information made the initial view easier to scan, but added a step to reach deeper properties. Keeping definitions and examples alongside one another helped preserve context as developers explored.

We prioritized understanding before measuring efficiency.

Within the project timeline, the research team recommended qualitative research for the proof of concept. That helped inform the design direction, but we did not establish a quantitative comparison of task time or errors.

My next step would be to test the journey from finding fields to building a request. Comparing completion, incorrect field selections, and backtracking would help assess the redesign. I would also check whether developers discover the highlighting toggle and understand its relationship to the selected example.

I found my way through complexity by looking for patterns.

I did not need to understand every technical detail at once to begin. Comparing recurring structures helped me ask more focused questions and build a component that accommodated both shared elements and differences.

Collaboration made the design stronger. A fellow designer’s suggestion connected examples to the reference in a way that the structure alone could not. This project reinforced how much a clear foundation and timely context can do together.
